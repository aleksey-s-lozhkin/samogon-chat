# Работа с «Самогоном» в облачной среде

Быстрый маршрут для временного облачного рабочего окружения, включая Codex
Cloud. Здесь только разработка и проверки; production-ключи, дампы, медиа и
файлы сессий в облачную задачу не копируются. Общий контекст — в [memory.md](memory.md).

## Подготовка окружения

Нужны Python 3.14 и Poetry. Сначала проверьте ветку и только при необходимости
установите зависимости (не повторяйте установку в уже готовой среде):

```bash
git status --short --branch
python --version
poetry --version
# Если зависимости ещё не установлены:
poetry install --no-interaction --no-root --with dev
```

Для базовой локальной разработки достаточно SQLite и значений из
`.env.example`. Production env-файл не копируйте. Redis, PostgreSQL, Docker,
Ollama, OAuth, Turnstile и Web Push нужны только для сценариев, которые их
непосредственно проверяют; отсутствие этих сервисов не должно блокировать
обычную правку шаблона или серверной логики.

## Проверки по стоимости

Сначала запустите тест изменённого приложения или класса, затем Django check:

```bash
poetry run python manage.py test chat.tests.NotesViewTests  # замените на нужный класс
poetry run python manage.py check
```

Для API выполните `poetry run python manage.py spectacular --validate`.
Для изменения интерфейса установите браузеры один раз и запустите smoke:

```bash
poetry run playwright install chromium webkit
poetry run python scripts/browser_smoke.py
```

Smoke использует временную SQLite-базу и локальный порт `127.0.0.1`, не
production. Полный `manage.py test` запускайте локально при изменении нескольких
подсистем или настройках; обычный PR проверяет полный набор в
`.github/workflows/ci.yml`. Если браузеры или порт недоступны, сообщите
ограничение; не обходите TLS или другие защитные настройки.

## Ветки и выпуск

- Новую работу начинайте от обновлённого `develop`; одна ветка и один PR решают
  одну задачу. Перед сдачей проверьте отсутствие лишних файлов и `git diff --check`.
- PR в `develop` проверяет Django, браузерный smoke-test и сборку образа.
- Merge в `main` запускает `.github/workflows/publish-deploy.yml` и может
  изменить production. Не используйте `main` как базу для пробной правки и не
  считайте успешный PR-деплой подтверждением пользовательского сценария.
- После публикации образа проверяйте точный SHA и затронутый маршрут по
  [release checklist](docs/release-checklist.md). Результаты прошлых образов
  не подтверждают новый образ.

Для полной схемы сервисов и эксплуатации см. [архитектуру](docs/architecture.md)
и [инструкцию по развёртыванию](docs/deployment.md). Реальные адреса, доступы и
секреты хранятся вне репозитория.
