# Память проекта «Самогон»

Короткий контекст для новой задачи: сначала прочитайте этот файл, затем только
затронутые разделы документации и кода. Не перечитывайте весь ТЗ или старые
диалоги без конкретной причины. Факты о Git и production всегда проверяйте
заново; секреты и пользовательские данные сюда не записываются.


> **Одно из трёх связанных приложений.** Рядом — лапоть (главное) и **Сито**
> (`sito`, бывший DocSearch — поиск по документам).
> У всех **одна видеокарта на 8 ГБ, один сервер и один реестр образов**, а
> чат-модель — **одна на всех**: `qwen3:8b` с одинаковым `num_ctx`. Для
> эмбеддингов у соседей свои маленькие модели (у лаптя `nomic-embed-text`, у
> Сита `bge-m3`), и рядом с общей они в 8 ГБ помещаются. Поэтому приложения
> мешают друг другу, хотя лежат в разных репозиториях.
>
> **Картина целиком и договор о работе — в
> [`lapot/docs/PROJECTS.md`](../lapot/docs/PROJECTS.md)
> (<https://github.com/aleksey-s-lozhkin/lapot/blob/main/docs/PROJECTS.md>):
> относительный путь работает, когда репозитории лежат рядом, ссылка — всегда.**
> Читать перед работой, которая задевает соседей: сменой модели, настройками
> Ollama, поиском, деплоем, инфраструктурой.
>
> Правило: **решение живёт в том репозитории, где его исполняют** — и попадает
> в этот документ ссылкой.

## Что это за приложение

«Самогон» — веб-чат для разработчиков. Сервер написан на Django; Channels и
WebSocket доставляют сообщения, PostgreSQL хранит данные, Redis поддерживает
соединения и фоновые задачи, Celery выполняет отложенную работу. Веб-интерфейс
использует серверные шаблоны, HTMX и JavaScript. Семён — локальный ИИ-бармен
через Ollama. Есть версионированный HTTP API для мобильного клиента.

Основные каталоги: `chat/` — комнаты, сообщения, заметки, WebSocket и Семён;
`users/` — аккаунты, профиль и Push; `config/` — настройки и маршруты;
`static/` и `templates/` — интерфейс; `deployment/` — развёртывание.

## Принятые решения

- Открытая регистрация управляется `REGISTRATION_OPEN`; изменение переменной
  требует пересоздания контейнеров штатным deploy. Проверка email при
  регистрации пока не вводилась. Регистрация требует галочку 18+ и согласия
  с правилами; дата и версия принятой редакции сохраняются в аккаунте.
- `DEBUG` по умолчанию `0`, а `SECRET_KEY` и `DATABASE_URL` обязательны вне
  DEBUG. Локально значения берутся из `.env`, который читается автоматически.
  Тесты и браузерный smoke сохраняют режим разработки через `manage.py test`.
- Состояние присутствия разделено: `online_users` — онлайн конкретной беседы,
  `user_presence` — глобальный справочник для свёрнутого списка «Отошли».
- Вложения-документы всегда скачиваются, а не открываются внутри origin.
  Расширение `.js` не принимается: раньше inline-выдача давала stored XSS.
- В закрытой беседе ограничения на число приглашённых нет: действует только
  «минимум один участник». Раньше форма требовала одного-двух, из-за чего
  беседа с большим составом вообще не сохранялась.
- Свой текстовый статус меняется в профиле. В панели гостей остался только
  быстрый выбор из справочника: инлайновое поле было тесным и вызывало
  автоматический зум Safari на телефоне.
- Изображения вложений открываются в общем модальном окне (чат и личные
  заметки) с кнопкой сохранения. Ссылка остаётся запасным путём без JavaScript.
- Браузерный smoke использует временный `MEDIA_ROOT`, поэтому тестовые вложения
  больше не попадают в рабочий каталог `media/`.
- Смена статуса с HTTP-страницы профиля рассылает снимок присутствия по
  WebSocket: иначе другие гости видели прежний статус до перезагрузки.
  Снимок «до» берётся до `form.is_valid()` — валидация уже подменяет поля
  instance данными формы.
- Палитра реакций и набор emoji в composer расширены; допустимые реакции API
  берёт из модели `MessageReaction.Emoji`, чтобы список не расходился.
- Кнопка «Войти в бар» на главной ведёт гостя на страницу входа с возвратом
  в `/chat/`, а не сразу в список комнат.
- Изображения хранятся в двух разрешениях: оригинал и превью до 640 px по
  длинной стороне. Лента грузит превью, просмотр и скачивание — оригинал.
  Превью не создаётся, если после перекодирования оно выходит не меньше
  оригинала: иначе мелкая картинка стала бы тяжелее.
- Птица-Говорун отложена до отдельного решения. Согласованы рамки: только одна
  комната на обкатку, выключено по умолчанию, курируемый список поводов вместо
  RSS, тихие часы по одному эталонному поясу (комната общая — «ночь для всех»
  определить нельзя), ботов и суперпользователей не считаем гостями. Это
  дизайн будущей птицы, к персональным тихим часам уведомлений он отношения
  не имеет. Подробности и обоснования — в `docs/product-specification.md`.
- Проверка языка ответа бармена вынесена в `chat/services/language.py` без
  зависимостей от Django: раньше она была скопирована в трёх местах и
  расходилась. Пунктуация CJK теперь тоже считается иероглифами.
- Текущая страница чата подгружает старые сообщения по мере прокрутки. Личные
  заметки доступны только владельцу; поиск по ним работает в браузере, без
  отправки поискового запроса на сервер.
- При отказе WebSocket из-за истёкшего входа интерфейс предлагает войти снова
  с возвратом в ту же комнату. Один лишь код `403` в журнале Nginx не доказывает
  причину отказа: нужны состояние сессии и серверные признаки авторизации.
- **Общая чат-модель с соседями — `qwen3:8b`, и это условие, а не вкус.**
  Семён, лапоть и Сито делят одну видеокарту 8 ГБ, поэтому приложение обязано
  звать базовую модель, а не собственный профиль `samogon-semen-*`: профиль в
  Ollama — отдельная модель, её загрузка вытесняет общую, и сосед платит
  двадцатью секундами холодной загрузки. По той же причине `OLLAMA_NUM_CTX`
  (8192) совпадает с лаптем: это параметр загрузки, и расхождение заставляет
  Ollama перезагружать модель на каждом переходе между приложениями (замерено
  4,2 с в каждую сторону). `OLLAMA_TIMEOUT_SECONDS` поднят с 20 до 60 —
  двадцать равнялись времени загрузки, и первый запрос после паузы отдавал
  гостю заготовку вместо ответа. Характер уходит системным сообщением из
  `chat/services/prompts/semen.txt`, а не полем модели. Условия закреплены
  дешёвыми тестами: `chat/tests_model_contract.py` здесь и
  `tests/test_model_contract.py` у лаптя — ломка тихая, всё продолжает
  работать, только в разы медленнее. Замеры — в `docs/bartender-quality.md`.
  **Эмбеддинги — это не чат-модель**: у Сита к отрывкам `bge-m3`, у лаптя
  `nomic-embed-text`; обе маленькие и рядом с `qwen3:8b` (6,19 ГБ из 8)
  помещаются.
- **Защитный слой Семёна отвечает раньше модели.** Медицинский риск, просьба
  показать внутренние инструкции, запрос секретов, разрушительные команды,
  грубая самооценка и прямые оскорбления получают предсказуемый ответ из
  `chat/services/bartender_guardrails.py`, не доходя до Ollama. Одинаковый
  отпор на одинаковый выпад — правильное поведение, а не дефект: на замере
  27 из 39 повторов дал именно защитный слой.
- Семён должен отвечать коротко, естественно, по-русски и в образе бармена.
  Изменения его поведения проверяются на реальной модели наряду с тестами.
- **Базовая линия промпта — 78 из 90 ответов (86,7 %), 30 сценариев по три
  повтора.** Абстрактные запреты не работают, работают примеры «Гость: …
  Ответ: …»; `think:true` Семёну вредит (проходит около половины, время растёт
  вдесятеро). Прежняя запись «все 60 ответов прошли машинные стоп-факторы»
  описывала промпт, которого больше нет. Таблица прогонов и разбор — в
  `docs/bartender-quality.md`.
- Production-данные, ключи, cookie и закрытые адреса не копируются в репозиторий
  или публичные отчёты. Внешние уведомления не содержат текст сообщений.
- Резервные копии всех трёх проектов снимает один скрипт —
  `/srv/scripts/backup-projects.sh`, версия в репозитории лаптя
  (`deploy/backup-projects.sh`). Дамп базы, архив файлов и **архив окружения с
  секретами**, всё под AES-256 с ключом из отдельного файла
  `/srv/config/backup.key`. База копируется по имени: Postgres на сервере
  общий с другими проектами. Проверка — `--verify <проект> [метка]`:
  копия расшифровывается, разворачивается в одноразовый контейнер Postgres и
  удаляется, рабочая база не затрагивается. Метка выбирает конкретную копию —
  проверять только свежую бессмысленно, она сломаться ещё не успела.
- Уведомление модераторам о новой жалобе уходит после фиксации транзакции и
  через очередь. Раньше сетевые запросы ко всем модераторам выполнялись внутри
  `@transaction.atomic` под блокировкой строки сообщения: транзакция и
  соединение с базой ждали push-службу.
- Web Push уходит через Celery. Раньше общая рассылка из админки выполнялась
  прямо в запросе и ждала push-службу, а личное уведомление жило фоновой
  задачей внутри веб-процесса и терялось при перезапуске. Через очередь идут
  все виды: личное сообщение, сообщение в открытой комнате и уведомление
  модераторам о жалобе. Если брокер недоступен, отправка падает обратно в
  текущий процесс — лучше задержка, чем молча потерянное уведомление.
- **Уведомления: три режима на устройство, тишина — на человека.** У подписки
  `PushSubscription.Mode` три значения: `off`, `direct`, `all`. Выбор из трёх,
  а не два флажка: с двумя получалось состояние «разрешено, но ни о чём не
  сообщать» — человек его выставлял, ничего не происходило, и почему, понять
  было нельзя. Тихие часы и часовой пояс живут в `NotificationSettings`, а не
  в подписке: **спит человек, а не телефон**, иначе ноутбук будил бы среди
  ночи, пока телефон молчит, а на новом устройстве тишину пришлось бы
  настраивать заново. Решение «слать или нет» собрано в одном месте —
  `users/services/notifications.py` — и возвращает причину: выключено, тихие
  часы, человек сейчас в приложении. Присутствие проверяется последним: это
  единственный поход в Redis, и при тихих часах он не нужен. Часовой пояс,
  названный с ошибкой, тишину не роняет: берётся пояс проекта. Уведомления о
  комнате уходят только подпискам `all`, не называют отправителя и
  склеиваются по `tag` комнаты, чтобы десять сообщений подряд не висели
  десятью строками.
- Логирование: `django.request` на уровне ERROR (5xx без шума 404/403) и
  `django.security` на WARNING. Уровни настраиваются окружением.
- Добавлены индексы под постоянные запросы: история комнаты, личные сообщения и
  очередь нерассмотренных жалоб.

## Быстрый маршрут

1. Проверьте `git status --short --branch` и **обе** ветки, `origin/develop` и
   `origin/main`. Схема «работа в develop, релиз в main» соблюдается не всегда:
   8–9 октября правки (общая модель, промпты, уведомления, жалобы) ушли прямо
   в `main`, и `develop` отставал на десятки коммитов. Документ, сверенный по
   одной ветке, описывал код, которого в ней нет. Свежее не то, что положено
   по схеме, а то, где код. Старый SHA не подтверждает текущий deploy.
2. Найдите нужный код через `rg`, откройте только релевантные файлы. Для границ
   задачи обращайтесь к [ТЗ](docs/product-specification.md), для потоков данных —
   к [архитектуре](docs/architecture.md). [Статус релиза](docs/release-status.md)
   датирован 26.09.2026 и не является актуальным списком блокеров.
3. Для одной задачи создайте отдельную ветку от свежей базы. По договору это
   `develop`; если он отстал от `main` (см. пункт 1), берите `main` или ветку,
   которая их сводит. После merge не продолжайте работу в старой
   feature-ветке.
4. Сначала запустите узкие тесты. Браузерный smoke нужен при изменении UI;
   полный набор выполняет CI. Не повторяйте успешно пройденные длительные
   проверки без нового изменения или диагностической гипотезы.
5. В отчёте различайте «проверено локально», «слито в `develop`» и
   «доставлено в production».

Команды — в [cloud.md](cloud.md) и [документации по тестированию](docs/testing.md).
Production-проверка — в [release checklist](docs/release-checklist.md). Этот
файл не назначает приоритет задачам из ТЗ.
