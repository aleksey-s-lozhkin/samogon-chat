# Администрирование и модерация

## Интерфейсы

`/admin/` — управление системой через Jazzmin: единая светлая серая тема,
графитовое меню и русские названия моделей, полей и действий. Пользовательская
тема чата на админку не влияет. Локальный каталог `locale/ru/LC_MESSAGES/`
дополняет отсутствующие переводы Django; после изменения `.po` нужно обновить
поставляемые `.mo` для обоих каталогов:

```bash
msgfmt locale/ru/LC_MESSAGES/django.po -o locale/ru/LC_MESSAGES/django.mo
msgfmt locale/ru/LC_MESSAGES/djangojs.po -o locale/ru/LC_MESSAGES/djangojs.mo
```
 Большие таблицы прокручиваются внутри своей
области; повседневная работа с жалобами вынесена в отдельный интерфейс.

`/moderation/` — страница внутри существующей PWA. Отдельная установка и
учётная запись не нужны. Вход доступен из меню чата, счётчика жалоб и верхнего
меню админки. Нейтральное push-уведомление о новой жалобе ведёт сюда же.

Очередь разделена на новые и рассмотренные жалобы; несколько жалоб на одно
сообщение объединены в карточку. Новые жалобы показываются от старых к новым,
по 20 сообщений на странице. Desktop показывает очередь и карточку рядом,
телефон — отдельные экраны. Возврат в список сохраняет номер страницы и ведёт
к карточке сообщения.

## Статусы пользователей

В `/admin/users/chatstatus/` находится справочник «Статусы в чате».
Администратор может добавлять варианты, редактировать название, порядок и
флажок «Доступен для выбора». Код задаётся один раз (латиница, цифры, дефис
или подчёркивание, до 24 символов) и после создания не меняется. Удаление
заменено отключением: уже назначенные статусы остаются читаемыми, а новые
пользователи не могут выбрать отключённый вариант. Текущий отключённый статус
можно сохранить при редактировании профиля или сбросить через «Без статуса».

В карточке пользователя раздел «Профиль в чате» позволяет администратору
изменить или сбросить его статус. Модератор по-прежнему не редактирует профиль
и не получает права управления справочником автоматически. Обновлённые
подписи видны после следующего обновления присутствия; список выбора на уже
открытой странице обновляется при её перезагрузке.

Миграция `users.0010_chatstatus_alter_user_presence_status` создаёт справочник
и переносит шесть исходных вариантов без изменения статусов пользователей.
Профиль, WebSocket и API используют этот справочник вместо фиксированного
набора. При откате на старый код новые варианты не будут доступны для выбора;
таблица справочника должна сохраняться до завершения проверки выпуска.

## Права и приватность

- Просмотр: активный пользователь с `chat.view_messagereport`.
- Решения и восстановление: дополнительно `chat.moderate_message`.
- Блокировка: дополнительно `users.change_user` и членство в `Moderators`
  либо superuser. Обычного `is_staff` недостаточно.
- Группу с базовым набором прав создаёт существующая команда
  `python manage.py setup_moderators`; назначение пользователю выполняет
  администратор. Для самой PWA-страницы `is_staff` не требуется.
- Модератор видит обжалованное сообщение и его вложения, включая сообщение
  из личного диалога или закрытой беседы. Соседняя переписка не загружается.
- Вложения скачиваются через отдельный защищённый маршрут, который проверяет
  право просмотра жалоб и принадлежность файла обжалованному сообщению.
  Обычные маршруты вложений и правила доступа участников не расширяются.
- Страницы и файлы модерации отвечают с `Cache-Control: no-store`; service
  worker сохраняет только публичную оболочку и статику, не жалобы.

## Решения

У каждого решения обязательны причина (до 240 символов) и подтверждение.

1. **Отклонить жалобу** — закрывает все новые жалобы на сообщение, оставляет
   сообщение доступным.
2. **Скрыть сообщение и закрыть жалобы** — сохраняет сообщение для проверки,
   убирает его из чата и закрывает новые жалобы.
3. **Заблокировать автора и закрыть жалобы** — сутки, неделя либо бессрочно.
   Можно одновременно скрыть сообщение (флажок включён по умолчанию).
   Если флажок снят, сообщение остаётся доступным.
   Нельзя блокировать себя, staff, superuser или другого участника Moderators.
4. **Восстановить сообщение** — доступно из рассмотренной жалобы, если оно
   скрыто. Исходный итог рассмотрения сохраняется; восстановление добавляется
   отдельной записью журнала. Реплика появляется при следующей загрузке
   истории, без отправки нового уведомления.

`MessageReport` хранит итог, комментарий, автора и время решения. Старые
рассмотренные жалобы без итога показываются как «Рассмотрено ранее».
`ModerationEvent` хранит действия, включая рассмотрение жалоб.

Общий сервис `chat/services/moderation.py` используется и PWA-страницей,
и действиями админки. Решения выполняются транзакционно, с блокировкой строки
сообщения в PostgreSQL. Создание новой жалобы использует ту же блокировку.
Повторное или устаревшее решение возвращает HTTP 409, не перезаписывая первое.
Скрытие передаётся подключённым клиентам после фиксации транзакции.

При отсутствии сети форма недоступна. При обрыве ответа показывается, что
результат не подтверждён: нужно обновить страницу перед повтором. Офлайн-очереди
решений нет. При отключённом JavaScript работает обычная HTML-форма с CSRF.

## Проверка и выпуск

```bash
poetry run python manage.py check
poetry run python manage.py makemigrations --check --dry-run
poetry run python manage.py test chat.test_moderation config.test_admin
poetry run python scripts/moderation_smoke.py
```

Браузерный сценарий использует временную SQLite-базу и локальный сервер;
проверяет desktop Chromium, mobile Chromium 390 px и WebKit 320 px: очередь,
скрытие/восстановление, отсутствие связи, отсутствие горизонтального
переполнения страниц админки. Снимки содержат только тестовые данные и
сохраняются в `test-results/moderation-smoke/`.
SQLite-тесты проверяют конфликт устаревших решений последовательно;
реальную конкуренцию транзакций PostgreSQL они не моделируют.

Перед выпуском применить новые миграции `chat` и `users` штатным deploy,
обновить static и проверить точный образ web/worker. Миграции добавляют поля
решений и русские метаданные; прежние жалобы сохраняются. Новые поля имеют
пустое значение по умолчанию на уровне БД: предыдущий образ может создавать
жалобы после отката приложения.

На реальных iPhone/Android PWA проверить вход модератора, переход из push,
длинную жалобу, клавиатуру, скачивание вложения, возврат из фона и сохранение
решения. Отдельно двумя модераторами открыть одну жалобу и одновременно
отправить разные решения: второе должно получить конфликт, а история —
сохранить первое решение. Браузерная эмуляция не заменяет эту приёмку.

## Жалобы на пользователя из мобильного клиента

`/admin/users/userreport/` — отдельный список с фильтром новых/рассмотренных жалоб.
Переход «Жалобы на пользователей» находится в меню чата у модератора с правом
просмотра. Причина, заявитель и текст жалобы неизменяемы. Модератор заполняет
«Решение»: сохраняются его аккаунт и время рассмотрения. Повторное устаревшее
решение не перезаписывает первое. Бан не назначается автоматически: при
необходимости используется существующее действие в карточке пользователя.

После миграции `users.0011_personalblock_userreport` права группы Moderators
обновляет `python manage.py setup_moderators`; штатный entrypoint уже вызывает
эту команду. Ручной запуск нужен только при отдельном применении миграций.
Этот выпуск не объединяет пользовательские жалобы с очередью `/moderation/`
и не отправляет о них push. Персональные блокировки являются настройкой видимости
владельца, не административным ограничением аккаунта.
