# Быстрый рабочий процесс до релиза

Цель процесса — короткая обратная связь без снижения надёжности. До открытой
беты действует feature freeze: новый продуктовый scope не добавляется, кроме
исправления release blocker.

## Размер изменения

- Одна ветка и один PR решают одну проблему.
- В PR не смешиваются feature, рефакторинг, документация и инфраструктура,
  если они не являются частями одного исправления.
- Перед началом проверяется актуальный `develop`, а после merge старая ветка не
  используется для новых коммитов: создаётся новая ветка от `develop`.
- Длинное исследование заканчивается короткой записью: причина, доказательство,
  принятое решение и следующий шаг.

## Уровни проверки

### Уровень 1 — во время разработки

Запускаются только тесты изменённого модуля или test case. Цель — результат за
секунды или несколько минут.

### Уровень 2 — перед PR

Запускаются Django checks, тесты затронутого приложения и нужный smoke. Полный
набор выполняет CI. Локальный полный набор нужен, если изменение пересекает
несколько приложений, настройки, миграции или WebSocket-протокол.

### Уровень 3 — release candidate

Backup/restore, production load 30 + 30, проверка Семёна и ручная матрица
выполняются один раз для точного SHA-кандидата. Успешный этап не повторяется,
если его код и конфигурация не менялись.

## Работа с длительным или упавшим тестом

1. Сначала выполняется короткий preflight одного клиента.
2. Длительный тест запускается только после успешного preflight.
3. При первой ошибке сохраняются JSON теста, состояние контейнера, ресурсы и
   журналы за последние 10 минут.
4. Тот же тест не запускается повторно без новой гипотезы или исправления.
5. Генератор нагрузки проверяется отдельно от производительности приложения:
   30 + 30 измеряет чат без Семёна, модель проверяется одним клиентом.

## Работа с Codex

- Для новой темы создаётся новая задача с одним ожидаемым результатом.
- Большой завершённый диалог не продолжается бесконечно: новый диалог начинает
  работу с `docs/release-status.md`, названием ветки и последним SHA.
- Вместо длинной переписки с терминалом прикладывается один файл вывода либо
  точная ошибка и последние 100–200 строк нужного сервиса.
- В запросе сразу указывается режим: `диагностика без исправления`,
  `исправить и проверить`, `только инструкции для сервера` или
  `подготовить ветку и PR`.
- Для независимых задач можно использовать отдельные задачи параллельно, но
  одна и та же ветка не редактируется одновременно несколькими задачами.

## Рекомендуемый режим до выпуска

1. Закрыть четыре пункта из `release-status.md`.
2. Зафиксировать точный SHA и результаты в журнале релиза.
3. Не добавлять Redis-кэши, шум бара, расширение заметок и новые OAuth до
   выпуска.
4. После успешного smoke исправлять только release blocker.
