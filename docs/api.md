# HTTP API

API предназначен для диагностики и будущих клиентов. Текущая версия доступна
под `/api/v1/`; несовместимые изменения получают новый префикс версии.

## Документация

- `/api/docs/` — интерактивный Swagger UI;
- `/api/schema/` — OpenAPI schema.

Схема публична и не содержит endpoint подписок, криптографических ключей,
секретов окружения или персональных данных. Защищённые операции используют
текущую Django-сессию. Для изменяющих запросов необходим CSRF cookie и заголовок
`X-CSRFToken`.

## Маршруты

### `GET /api/v1/chat/rooms/`

Возвращает только доступные текущему пользователю открытые комнаты и закрытые беседы,
включая число непрочитанных личных сообщений.

### `GET /api/v1/chat/rooms/{slug}/participants/`

Возвращает адресатов для личного сообщения в доступной комнате. Необязательный
`q` ищет по имени аккаунта без учёта регистра (до 50 символов). Ответ содержит
первые 50 записей `participants` с `username` для отправки и `display_name` для
интерфейса, а также `has_more`. Текущий пользователь, неактивные, заблокированные
и административные аккаунты исключены. В закрытой беседе возвращаются только её
участники. Требуется сессия; недоступная беседа возвращает `404`.

### `GET /api/v1/chat/rooms/{slug}/messages/`

Возвращает до 50 последних доступных реплик. Параметр `limit` принимает значения
от 1 до 100. Чужие личные сообщения и закрытые беседы не раскрываются.
В репликах поля `author_username` и `recipient_username` содержат имена
аккаунтов для адресации, а `username` и `recipient` — отображаемые имена.

### `POST /api/v1/chat/rooms/{slug}/messages/`

Создаёт обычную или личную реплику. Поля: `message`, необязательные `recipient`
и `reply_to`. Ответ на личную реплику автоматически сохраняет того же
собеседника. Сообщение сразу передаётся подключённым WebSocket-клиентам.

### `GET /api/v1/users/me/`

Возвращает безопасную публичную часть текущего профиля без email и прав доступа.

### `PATCH /api/v1/users/me/`

Изменяет выбранный статус пользователя. Принимает поле `presence_status`: код
доступного варианта из справочника «Статусы в чате» или пустую строку для
сброса. Неизвестные и отключённые варианты возвращают `400 invalid_request`.
Существующий отключённый статус продолжает отображаться в `GET`, пока
пользователь его не изменит. Подписи статусов редактируются в админке.

### `GET /api/v1/status/`

Возвращает версию API, состояние приложения, признак текущей авторизации и
доступность Web Push. Маршрут не требует входа.

### `GET /health/live/`

Проверяет только способность ASGI-процесса принять HTTP-запрос. Возвращает
`200` и `{"status":"ok"}`. Не обращается к внешним зависимостям.

### `GET /health/ready/`

Проверяет соединение с PostgreSQL и настроенным cache backend — Redis в
production. При полной готовности возвращает `200`; при недоступности хотя бы
одного компонента — `503`. Ответ содержит только `ok` или `unavailable`, без
адресов, имён баз, версий и текста исключений. Оба health-маршрута публичны,
не изменяют предметные данные и запрещают кэширование ответа.

Celery worker не входит в readiness web-процесса: он проверяется отдельно на
уровне контейнера, чтобы недоступность фоновых ответов Семёна не маскировалась
перезапуском работающего HTTP-сервиса.

### `GET /api/v1/push/subscriptions/`

Возвращает только устройства текущего пользователя. Вместо адреса push-службы
используется непрозрачный `device_id`. Требуется активная сессия.

### `POST /api/v1/push/self-test/`

Принимает `device_id` из предыдущего ответа и отправляет нейтральное тестовое
уведомление только на принадлежащее пользователю устройство. Запрос защищён
CSRF и ограничением частоты.

## Ошибки

Ошибки имеют короткий машинный код в поле `error`. Основные статусы: `400` для
неверного тела, `401` без сессии, `403` для недоступного аккаунта или CSRF,
`404` для чужого/неизвестного устройства, `429` при ограничении частоты и `503`
при отключённом Web Push. Внутренние исключения инфраструктуры клиенту не
передаются.

### Реакции и жалобы

- `POST /api/v1/chat/rooms/{room_slug}/messages/{message_id}/reactions/` —
  поставить или снять одну из разрешённых реакций: 👍, 👎, ❤️, 😂, 🔥, 😮,
  😢, 🤔, 🤝 или 🎉. Ответ возвращает новый
  счётчик и отображаемые имена участников; изменение сразу отправляется
  подключённым WebSocket-клиентам.
- `POST /api/v1/chat/rooms/{room_slug}/messages/{message_id}/reports/` — создать
  жалобу с причиной и необязательным комментарием до 240 символов. Повторная
  жалоба того же пользователя не создаёт дубликат и не отправляет новый push
  модераторам.

Обе операции разрешены только для видимой пользователю неудалённой реплики.
Чужие личные сообщения и комнаты возвращают `404`, не подтверждая их
существование. На собственную реплику пожаловаться нельзя.

### Вложения

`POST /api/v1/chat/rooms/{room_slug}/messages/{message_id}/attachments/`
принимает `multipart/form-data` с одним или несколькими полями `files`. Добавлять
файлы может только автор видимой неудалённой реплики. Сервер проверяет весь
набор до сохранения: при ошибке одного файла не сохраняется ни один.

Разрешены проверяемые изображения JPEG, PNG и WebP, PDF, а также ограниченный
набор текстовых форматов. Действуют те же ограничения размера, количества и
частоты, что в Web-интерфейсе. Ответ содержит только безопасные метаданные и
защищённые URL просмотра/скачивания — внутренний путь хранилища не раскрывается.
После успешной загрузки открытые клиенты получают WebSocket-обновление.

### Личные заметки

- `GET /api/v1/chat/notes/` — список только собственных заметок с безопасными
  ссылками на личные копии вложений;
- `POST /api/v1/chat/notes/` — создать текстовую заметку полем `text` либо
  сохранить доступную реплику полем `source_message_id`. Нужно передать ровно
  одно из этих полей;
- `DELETE /api/v1/chat/notes/{note_id}/` — удалить только собственную заметку.

Повторное сохранение одной реплики возвращает уже существующую заметку. При
первом сохранении вложения копируются в личное хранилище, поэтому последующее
скрытие исходной реплики не удаляет содержимое заметки.

### Семён и фоновые задания

- `POST /api/v1/chat/rooms/{room_slug}/bartender/jobs/` принимает `message` и
  необязательный флаг `private`, сохраняет вопрос и возвращает `202 Accepted`;
- `GET /api/v1/chat/bartender/jobs/{job_id}/` возвращает только владельцу
  состояние `queued`, `started`, `succeeded` или `failed` и ID сообщений.

API и WebSocket используют одну очередь. Отдельный worker обращается к Ollama,
повторяет временно неудавшееся задание и публикует ответ через WebSocket.

## Ограничения первой версии

Готовый ответ читается как обычная реплика из истории комнаты. API не
возвращает промежуточный поток токенов модели.

## Расширение API

Каждое приложение публикует собственный пакет `api/` и вызывает те же сервисы,
что Web и WebSocket. `config` подключает маршруты и собирает общую OpenAPI-схему;
предметная логика в `config` не переносится.

## Мобильный API: закрытые беседы и гости

Маршруты дополняют v1; прежний `GET /chat/rooms/`, PWA-формы и имена событий
присутствия сохраняются. Все пути ниже начинаются с `/api/v1/`. Авторизация —
Django session cookie, для POST/PATCH/PUT/DELETE обязателен `X-CSRFToken`.
Анонимный запрос получает JSON `401 authentication_required`; CSRF — JSON `403`.

| Метод и путь | Назначение |
| --- | --- |
| `POST chat/rooms/` | Создать одну собственную закрытую беседу |
| `GET chat/rooms/{room_slug}/` | Данные доступной беседы и права |
| `PATCH chat/rooms/{room_slug}/` | Изменить название и/или приглашённых |
| `DELETE chat/rooms/{room_slug}/` | Удалить собственную беседу |
| `POST chat/rooms/{room_slug}/leave/` | Выйти приглашённому участнику |
| `GET chat/guests/` | Допустимые аккаунты и online-снимок |
| `GET users/statuses/` | Доступные варианты статусов |
| `POST users/{user_id}/reports/` | Пожаловаться на пользователя |
| `GET users/me/blocks/` | Свои персональные блокировки |
| `PUT users/me/blocks/{user_id}/` | Заблокировать для себя |
| `DELETE users/me/blocks/{user_id}/` | Снять свою блокировку |

Создание принимает `{"name":"Наша беседа","member_ids":[12,34]}`. Требуются
название до 100 символов и 1–2 разных приглашённых; владелец добавляется
автоматически. Себя, неактивные, административные, забаненные аккаунты и Семёна
приглашать нельзя. PATCH принимает любое подмножество этих двух полей; пропуск
сохраняет текущее значение. Существующий участник может выйти, оставив владельца
одного; следующий PATCH требует снова указать 1–2 приглашённых.

Ответ создания (`201`), чтения и изменения (`200`) расширяет обычную запись
комнаты полями `owner`, `members`, `can_manage`, `can_delete`, `can_leave`.
Аккаунты содержат `id`, `username`, `display_name`; `members` включает владельца.
В публичной комнате `owner=null`, `members=[]`, все три права — `false`.
Чужая закрытая беседа возвращает `404 room_not_found`, включая попытки изменения.
Приглашённый не может управлять беседой (`403 room_management_forbidden`).
Повторное создание собственной беседы — `409 owned_room_exists`; выход владельца
— `409 owner_cannot_leave`. Невалидные данные — `400 invalid_room` с `fields`.
Удаление и выход возвращают `204`; повтор после утраты доступа — `404`.
Исключение, выход и удаление закрывают соответствующие WebSocket-соединения
кодом `4403` после фиксации транзакции, как в PWA.

`chat/guests/` возвращает `api_version`, `guests`, `online`, `has_more`,
`next_offset`. Поля гостя: `id`, `username`, `display_name`, `avatar_url`
(или null), `status_code`, `status`, `last_seen_at` (ISO 8601 или null).
`online` — имена онлайн-аккаунтов из того же допустимого набора, включая страницы
за пределами текущей; это снимок на момент запроса. Поддерживаются `q` до
50 символов, `offset>=0`, `limit=1..100` (по умолчанию 50).
Не раскрываются закрытые беседы; неактивные, административные, забаненные
аккаунты, Семён и лично заблокированные текущим пользователем исключены.
Семён остаётся отдельным известным клиенту участником; прежний API адресатов
сохраняет его доступность. Собственный допустимый аккаунт входит в список гостей.

`users/statuses/` возвращает `{"api_version":"v1","statuses":[{"code":"…",
"label":"…"}]}` в серверном порядке. Выбирать можно только активные варианты;
пустая строка для сброса передаётся в прежний `PATCH users/me/` отдельно.

## Жалобы на пользователя и персональная блокировка

Жалоба принимает `reason` (`abuse`, `spam`, `privacy`, `other`) и необязательный
`details` до 1000 символов. Создание — `201 {"reported":true,"created":true}`;
повторная нерассмотренная жалоба той же пары — `200` с `created:false`, исходный
текст сохраняется. После рассмотрения можно подать новую. Невалидная причина —
`400 invalid_report`, превышение лимита — `429 rate_limited`. Пожаловаться на
себя или недоступный аккаунт нельзя (`404 user_not_found`). Жалобы рассматриваются
в админке, отдельно от очереди жалоб на сообщения; push для них пока не отправляется.

PUT блокировки не требует тела, повтор идемпотентен (`204`). DELETE также всегда
`204`, в том числе для отсутствующей своей блокировки. Чужие блокировки не
изменяются. GET возвращает `api_version`, `blocks` (аккаунты с id/username/
display_name), `next_offset`; страницы по 50, параметр `offset`. Уже заблокированные
неактивные аккаунты остаются в собственном списке для возможности разблокировки.

Семантика блокировки:

- Новые личные сообщения запрещены в обе стороны через HTTP и WebSocket.
  Нельзя добавить вложение к прежнему личному сообщению этой пары; push не отправляется.
- Установивший блокировку не видит сообщения автора в истории, поиске, цитатах,
  реакциях и счётчиках непрочитанного; защищённые ссылки на его вложения дают 404.
  Собственные сообщения сохраняются. У второго участника прежняя история остаётся.
- Уже подключённый клиент получает новую `history`, `unread_snapshot` и
  `user_presence`. Отложенные сообщения проверяются повторно при доставке.
- Разблокировка восстанавливает доступ к существующей истории. Отклонённые
  сообщения не создавались и повторно не доставляются. Ранее сохранённые личные
  заметки остаются собственными копиями пользователя.
- Блокировка не является административным баном, не удаляет аккаунт и не
  исключает из закрытой беседы. Другие участники продолжают видеть его сообщения.

Схема генерируется из сериализаторов и аннотаций маршрутов; проверка:
`poetry run python manage.py spectacular --validate --fail-on-warn --file /tmp/samogon-openapi.yaml`.
Выпуск и приёмка: [mobile-api-release.md](mobile-api-release.md).
