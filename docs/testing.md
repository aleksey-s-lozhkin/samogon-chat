# Проверка проекта

## Серверные тесты

```bash
poetry run python manage.py check
poetry run python manage.py spectacular --validate
poetry run python manage.py test
```

## Браузерный smoke-test

Один раз установите браузерные движки:

```bash
poetry run playwright install chromium webkit
```

Запустите проверку:

```bash
poetry run python scripts/browser_smoke.py
```

Сценарий самостоятельно создаёт временную SQLite-базу и тестовых пользователей,
запускает локальный ASGI-сервер на свободном порту и удаляет данные после
завершения. Рабочая локальная и production-базы не используются.

Проверяются:

- вход через обычную форму;
- загрузка истории через WebSocket и отправка реплики;
- сохранение положения читаемого сообщения при подгрузке истории; проверка
  выбора сгруппированной реплики выполняется после пагинации, чтобы
  автоматическая прокрутка к ней не запускала загрузку до замера. Мобильная
  проверка действий удерживает ID сообщения при добавлении старой истории;
- переключение между собственной и приглашённой закрытыми беседами;
- потеря соединения при остановке сервера и автоматическое восстановление;
- положение composer внутри viewport на desktop Chromium, мобильном Chromium
  и мобильном WebKit.

При ошибке в `test-results/browser-smoke/` сохраняется снимок только временной
тестовой страницы. Cookies, Playwright trace и production-данные в артефакты не
записываются. В CI снимки доступны семь дней только как артефакт неуспешного
запуска.

## Проверка release candidate

Для production подготовлены отдельные безопасные инструменты:

- `scripts/verify_backup_restore.sh` создаёт backup базы и media и проверяет
  восстановление во временном PostgreSQL;
- `scripts/performance_audit.py` измеряет HTTP, WebSocket и ответы Семёна с 30
  активными и 30 неактивными временными клиентами;
- `scripts/production_smoke.py` проверяет публичные production-маршруты и при
  наличии временной сессии — авторизованный чат и WebSocket.

Полная последовательность, очистка тестовых данных и ручная проверка описаны в
[чек-листе release candidate](release-checklist.md).

Проверки разделены по стоимости, чтобы обратная связь не занимала часы:

1. При обычной правке запускать только тесты изменённого приложения или файла.
2. Перед push запускать затронутый Django test case и небольшой smoke, если
   менялся браузерный код.
3. Полный `manage.py test` и browser smoke выполняет CI; локально они нужны
   перед объединением нескольких подсистем или при нестабильном дефекте.
4. Production load, backup/restore и полный ручной smoke выполняются один раз
   на release candidate, а не после каждого PR.

Нагрузку чата и Семёна нужно измерять отдельно. Замер 30 + 30 использует
`--bartender-samples 0`; после него один клиент делает три запроса Семёну.
Так медленная локальная модель не скрывает характеристики HTTP/WebSocket.
При первой ошибке сохраняются отчёт и журналы конкретного этапа; слепой повтор
того же длительного сценария запрещён.

Файл audit-сессий внутри `/tmp` контейнера эфемерен и исчезает при deploy.
Между deploy защищённая копия хранится на production-хосте в `/srv/config/` и
при необходимости копируется обратно в новый `samogon-web`.

## Проверка production-контейнеров

После запуска образа проверьте состояния обоих сервисов:

```bash
docker compose ps
docker inspect --format '{{json .State.Health}}' samogon-web
docker inspect --format '{{json .State.Health}}' samogon-worker
```

Для ручной проверки web снаружи используются два маршрута:

```bash
curl --fail https://app.example.invalid/health/live/
curl --fail https://app.example.invalid/health/ready/
```

`live` подтверждает ответ Daphne, `ready` дополнительно проверяет PostgreSQL и
Redis. Worker отвечает на адресный Celery ping внутри Docker. Plain Docker
Compose показывает состояние `unhealthy`, но сам по этому признаку контейнер не
перезапускает; `restart: unless-stopped` применяется, когда процесс завершился.
Deploy workflow ждёт готовности обоих контейнеров и останавливает выкладку с
последними журналами соответствующего сервиса, если проверка не прошла. При
наличии единого предыдущего образа workflow автоматически возвращает web и
worker на него и обновляет Nginx. Миграции базы автоматически не откатываются,
поэтому перед релизом они должны сохранять обратную совместимость.

## Админка и мобильная модерация

```bash
poetry run python manage.py test chat.test_moderation config.test_admin
poetry run python scripts/moderation_smoke.py
```

Сценарий использует временные данные, проверяет серую админку и решения в
PWA на desktop/mobile Chromium и mobile WebKit. Права, CSRF, ограничение
доступа к вложениям, повторное решение и аудит проверяются серверными тестами.
Реальная конкуренция PostgreSQL и физические устройства проверяются отдельно
по [руководству модерации](moderation.md).

## Вложения, статусы и Семён в гостях

Адресная серверная проверка:

```bash
poetry run python manage.py test users.test_chat_status users.tests chat.tests.ChatConsumerTests chat.tests.ChatLayoutViewsTests config.test_admin
```

Проверяются исходные и новые статусы, их переименование/отключение, сохранение
текущих назначений, профиль, API, WebSocket и права администратора/модератора.
Общий browser smoke дополнен выбором обоих режимов Семёна из «Гостей»,
закрытием панели и фокусом ввода, прозрачностью вложения и размерами подсказки.
Он подготовлен для CI, но в этой задаче локально не запускался по просьбе
владельца не использовать браузер.

После deploy на телефоне и desktop:

1. Проверить файл в собственном, чужом и личном пузыре, в светлой и тёмной теме.
2. На ширинах 320/390 px проверить пустое поле и ввод с клавиатурой: подсказка
   полностью видна, адресат находится отдельно, ввод текста растёт по высоте.
3. Открыть «Гости» → «Семён», выбрать общее обращение, затем личное. Панель
   закрывается на телефоне; курсор в поле, строка адресата соответствует режиму.
4. В админке добавить и переименовать статус, изменить порядок, отключить его.
   После обновления чата новый статус доступен, отключённый нельзя выбрать
   заново, прежний статус пользователя сохранён. Проверить сброс в карточке.

## Мобильные API и персональные блокировки

`poetry run python manage.py test chat.test_mobile_api chat.test_mobile_safety`
проверяет JSON/CSRF, владельца/приглашённого/постороннего, ограничения участников,
повторы запросов, online-снимок, серверные статусы, жалобы и изоляцию блокировок.
Проверяются история/цитаты/реакции/поиск/вложения/непрочитанное/push, обновление
открытого WebSocket, отбрасывание отложенного события и отзыв доступа к комнате.
Тест production smoke использует реальные ответы Django и опубликованную схему
из тестового приложения, без браузера. Проверка продакшена описана в
[mobile-api-release.md](mobile-api-release.md).

SQLite проверяет последовательные сценарии. Конкуренцию строковых блокировок
PostgreSQL и работу реальных мобильных клиентов нужно подтвердить после деплоя.
