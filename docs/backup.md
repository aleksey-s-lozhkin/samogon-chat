# Резервные копии Самогона

Копии делает `deployment/backup/samogon-backup.sh`, проверяет и разворачивает
`deployment/backup/samogon-restore.sh`. Оба скрипта запускаются на хосте, где
работает `docker compose`, и не требуют зависимостей кроме `openssl`, `tar` и
`docker`.

## Два инструмента и их роли

В проекте есть ещё `scripts/verify_backup_restore.sh` — он живёт внутри образа и
используется при приёмке release candidate. Это не дубль, у них разные задачи:

| Инструмент | Что делает | Когда нужен |
|---|---|---|
| `scripts/verify_backup_restore.sh` | Снимает свежий дамп с боевой базы и сравнивает счётчики таблиц «источник против восстановленного», падая при расхождении | Приёмка релиза: убедиться, что база в принципе переносима |
| `deployment/backup/samogon-backup.sh` | Плановая копия: дамп, медиа, конфигурация, шифрование, ротация, выгрузка за пределы хоста | Ежедневно по расписанию |
| `deployment/backup/samogon-restore.sh` | Проверяет **уже сделанный архив** (в том числе зашифрованный) и умеет из него восстановить | Раз в месяц и перед рискованными изменениями |

Проверить чужой архив первым скриптом нельзя: он умеет только снимать новый
дамп. Оба используют один приём — разворачивают данные в одноразовый контейнер
Postgres, — и это сделано намеренно: общий сервер баз данных на хосте не
затрагивается.

## Что попадает в копию

| Часть | Как снимается | Зачем |
|---|---|---|
| База | `pg_dump -Fc` внутри контейнера Postgres | Люди, беседы, сообщения, заметки, жалобы |
| Медиа | `tar -czf` по `$SAMOGON_DATA_DIR/media` | Вложения, аватары, превью |
| Конфигурация | `.env.production` и `conf.d` nginx | Там секреты и маршрутизация; без них восстановление неполное |

**База копируется по имени, а не целиком.** Postgres на сервере общий с другими
проектами (nextcloud, diploma и так далее), поэтому `pg_dump` вызывается с
`-d "$DATABASE_NAME"`. Дамп «всех баз» здесь был бы и лишним, и опасным.

**Что не копируется:** `staticfiles` (пересобирается из образа) и сами образы
Docker (они лежат в реестре).

Все архивы шифруются AES-256-CBC с `pbkdf2` и 200 000 итераций. Ключ читается
из файла, в аргументах процесса и в истории команд он не появляется.

## Установка

```bash
# 1. Ключ шифрования. Храните его ОТДЕЛЬНО от копий: см. раздел ниже.
sudo install -d -m 700 /srv/config/samogon
openssl rand -base64 32 | sudo tee /srv/config/samogon/backup.key >/dev/null
sudo chmod 600 /srv/config/samogon/backup.key

# 2. Каталог копий
sudo install -d -m 700 /srv/backups/samogon

# 3. Первый прогон вручную — убедиться, что всё находится
cd /srv/samogon
sudo COMPOSE_DIR=/srv/samogon \
     SAMOGON_DATA_DIR=/srv/data/samogon \
     ./deployment/backup/samogon-backup.sh
```

Скрипт печатает, что делает, и в конце показывает содержимое каталога копий.
Если он не находит имя базы или контейнер Postgres — проверьте переменные
`WEB_CONTAINER`, `DB_CONTAINER` и `COMPOSE_DIR`.

### Расписание

```bash
sudo crontab -e
```

```cron
# Каждый день в 03:15. COMPOSE_DIR и SAMOGON_DATA_DIR задайте свои.
15 3 * * * COMPOSE_DIR=/srv/samogon SAMOGON_DATA_DIR=/srv/data/samogon \
  /srv/samogon/deployment/backup/samogon-backup.sh >> /var/log/samogon-backup.log 2>&1
```

Ротация встроена: `KEEP_DAYS` (по умолчанию 14) удаляет только собственные
архивы `*.enc` старше срока. Чужие файлы в каталоге не трогаются.

### Копия за пределы хоста

Пока копии лежат на том же диске, они не спасают от потери диска или сервера.
Скрипт умеет отправлять архивы через `rclone`, если задан `RCLONE_REMOTE`:

```cron
15 3 * * * COMPOSE_DIR=/srv/samogon SAMOGON_DATA_DIR=/srv/data/samogon \
  RCLONE_REMOTE=yandex:samogon-backups \
  /srv/samogon/deployment/backup/samogon-backup.sh >> /var/log/samogon-backup.log 2>&1
```

`rclone` нужно настроить заранее (`rclone config`). Если `rclone` не установлен
или копирование не удалось, скрипт пишет предупреждение и **не удаляет**
локальные архивы — потерять их из-за сетевой ошибки он не может.

## Проверка восстановления

Копия, которую ни разу не разворачивали, — это не копия, а надежда. Раз в месяц
и после любых изменений в схеме:

```bash
cd /srv/samogon
sudo ./deployment/backup/samogon-restore.sh --verify
```

Что происходит: берётся последняя копия (или указанная через `--stamp`),
расшифровывается и разворачивается **в одноразовый контейнер Postgres** — тот же
образ и та же версия, что у рабочего сервера, но с временной файловой системой в
памяти. Разворот идёт с `--exit-on-error`, поэтому повреждённый архив сразу
считается неудачей. Из восстановленной базы читаются счётчики людей, бесед,
сообщений, вложений, заметок и миграций, затем проверяется архив медиа. После
этого контейнер и распакованные файлы удаляются.

**Ни боевая база, ни общий сервер Postgres не затрагиваются:** временный
контейнер не имеет с ним ничего общего.

Посмотреть, какие копии есть:

```bash
sudo ./deployment/backup/samogon-restore.sh --list
```

## Настоящее восстановление

```bash
sudo ./deployment/backup/samogon-restore.sh --restore --stamp 2026-09-30-0315 --yes-i-know
```

Скрипт спросит подтверждение, остановит `samogon-web` и `samogon-worker` (чтобы
никто не писал в базу), развернёт дамп с `--clean --if-exists`, положит медиа
рядом и сохранит прежний каталог медиа как `media.before-restore-<метка>`,
запустит контейнеры обратно и скажет, что проверить.

Два флага нужны намеренно: без `--yes-i-know` скрипт откажется перезаписывать
боевую базу, а без `--restore` он вообще работает в безопасном режиме проверки.

## Ключ хранения

**Ключ нельзя держать там же, где архивы.** Если сервер потерян вместе с диском,
шифрование не спасёт: ключ уедет вместе с копиями. Минимум — сохранить ключ в
менеджере паролей и на другой машине. Без ключа архивы не восстанавливаются
вообще, поэтому потеря ключа равна потере копий.

## Что стоит знать

- **Шифрование защищает копии, но не заменяет права доступа.** Каталог копий —
  `700`, ключ — `600`.
- **Архив конфигурации содержит секреты** (`SECRET_KEY`, пароль базы, ключи
  VAPID, токены OAuth). Поэтому он шифруется вместе с остальными.
- **Место на диске.** Пайплайн деплоя требует минимум 5 ГБ свободными. Если медиа
  большое, следите за объёмом каталога копий: `KEEP_DAYS` считает дни, а не
  гигабайты.
- **Копия снимается на живой базе.** `pg_dump` даёт согласованный снимок, поэтому
  останавливать приложение для бэкапа не нужно.
