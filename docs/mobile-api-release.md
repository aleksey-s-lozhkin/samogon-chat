## Проверка опубликованной схемы и авторизованных GET

Использовать сохранённый `/srv/config/release-audit-sessions.json` с действующей
тестовой Django-сессией и правами файла 600. Файл содержит секреты: содержимое
не выводить и в отчёт не включать. Пример для существующего серверного расположения;
если контейнеру файл не смонтирован, передать его через `docker cp`:

```bash
sudo docker cp /srv/config/release-audit-sessions.json samogon-web:/tmp/mobile-api-sessions.json
sudo docker exec samogon-web chmod 600 /tmp/mobile-api-sessions.json
sudo docker exec samogon-web python scripts/production_smoke.py \
  --base-url https://sam.pyconstrictor.ru \
  --credentials /tmp/mobile-api-sessions.json --room general --mobile-api
```

`--room` должен быть slug существующей доступной публичной комнаты; заменить
`general`, если на сервере она называется иначе. Не использовать очищенную после
нагрузочного аудита комнату. При `401` обновить сессию тестового аккаунта, не
ослаблять авторизацию и не повторять нагрузочный тест.

Ожидается `status: ok`, блок `authenticated`, `mobile_api.schema: ok`, успешные
`guests`, `statuses`, `blocks` и число проверенных комнат. `private_rooms_checked: 0`
означает отсутствие доступной закрытой беседы у тестового аккаунта, а не успешную
проверку приватных прав. `mutations: not_run` — намеренно: smoke не создаёт беседы,
жалобы и блокировки. Он не доказывает работоспособность изменяющих сценариев.

## Авторизованная приёмка изменений после deploy

Для действий использовать три выделенных тестовых аккаунта: владелец, приглашённый,
посторонний. Запросы отправлять с сессией и CSRF из мобильного клиента/HTTP-клиента.

1. Владелец создаёт беседу с одним приглашённым (201). Повторное создание — 409.
   Приглашённый видит владельца/участников и can_leave, но PATCH/DELETE дают 403;
   посторонний получает 404 и не видит комнату в списке.
2. Владелец меняет название и приглашённых. Исключённому открытому WebSocket
   приходит закрытие 4403, новые HTTP-запросы дают 404. Пустой/тройной/дублированный
   список участников — 400. Выход владельца — 409; приглашённого — 204, повтор — 404.
3. Проверить online и изменение серверного статуса, затем старые формы PWA:
   название сохраняется без квадратных скобок, управление/выход продолжают работать.
4. Между двумя тестовыми пользователями создать личное сообщение и вложение.
   Установить блокировку (204, повтор 204). У блокирующего обновляются открытая
   история и счётчики; личная отправка в обе стороны отклоняется; push нет;
   старая ссылка на входящее вложение даёт 404. Третий пользователь видит публичные
   реплики как прежде. Снять блокировку (204) — старая история снова доступна.
5. Подать тестовую жалобу на пользователя (201), повторить (200, без дубля).
   Модератор открывает ссылку в меню и сохраняет решение в админке. Два одновременных
   решения сохраняют первое. Жалоба не должна автоматически банить пользователя.
6. Изменяющий запрос без CSRF — 403 JSON, без сессии — 401 JSON. После проверки
   снять тестовые персональные блокировки, удалить тестовую беседу владельцем;
   жалобу закрыть с отметкой о проверке. Реальные данные пользователей не изменять.

В отчёте указать точный образ, дату, `status` smoke, проверенные пункты, устройство
и оставшиеся ограничения. До этих действий состояние — «локально проверено,
production-приёмка ожидается».
